Window placement: one source per layout

A crash course in the change on branch feat-layout-apps-file (bead dc-20st, "Make each layout YAML the single source of window placement, including .fluxbox/apps"), and how it differs from what is on master.

In one minute
  • Before: two files placed windows. The layout YAML did it on relayout; the global .fluxbox/apps did it when a window first opened, using fixed head numbers that ignored the layout.
  • Now: each layout rule says where a window belongs (screen, workspace, position, size, sticky). One parser turns that into both the relayout commands and the apps-file placement.
  • The apps file is generated at every relayout from those rules plus a hand-written .fluxbox/apps.in that keeps only non-placement settings (Layer, Hidden, Deco, FocusProtection, ...).
  • The motivating bug is fixed: agent-browser now opens on the laptop in both Celtic+external layouts, whichever screen is primary.

The old problem

Fluxbox has two unrelated ways to place a window, and the config used both:

On relayout

Layout YAML

Each .fluxbox/layouts/*.yaml listed Fluxbox commands per window pattern. Placeholders such as <s_primary_col1_left> resolved to pixels for the screens actually connected. Layout-aware, but it only ran when the monitor setup changed.

On first open

.fluxbox/apps

One global file for every layout. [Head] takes only a number, and Fluxbox numbers the primary output head 1. So a rule saying "head 2" meant different physical screens in different layouts.

The concrete case

# master's .fluxbox/apps
[app] (name=google-chrome.*agent-browser-(data|chrome).*)
  [FocusProtection]	{Deny, Refuse}
  [Sticky]	{yes}
  [Head]	{2}          # laptop only while the external screen is primary
  [Position]	(UPPERLEFT)	{0 0}
[end]

Under celtic+external-secondary the laptop is primary, so it is head 1 and head 2 is the external screen. New agent-browser windows opened on the wrong monitor. A sandbox run of real Fluxbox with two heads reproduced exactly that.

The new model

Layout YAMLdeclarative window rules, per layout
→
Parser + resolverlayout.py: resolves screens, placeholders, heads
→
Relayout commandsMap {SetHead ...} {Matches ...}, applied to open windows
Apps attributes[Head], [Position], ... merged with apps.in into ~/.fluxbox/apps

Both outputs come from the same fields, so a window that opens after a relayout lands where the relayout would have put it. Every rule's head is resolved from the layout's own screen list, which is what fixes head-number drift.

Rule syntax, before and after

The chat-app rule from common/communication.yaml:

Before 
- - (Name=beeper|slack|Telegram|discord|Discord*|zulip)
  - MacroCmd {<s_primary_SetHead>} {SendToWorkspace 4}
      {MoveTo <s_primary_col1_left> <s_primary_row1_top>}
      {ResizeTo <s_primary_active_width> <s_primary_active_height>}
  - <unstick>

A matcher, then raw Fluxbox commands. (MacroCmd wrapped here for width; it was one line.)

After 
- match: (Name=beeper|slack|Telegram|discord|Discord*|zulip)
  screen: primary
  workspace: 4
  position: <s_primary_col1_left> <s_primary_row1_top>
  size: <s_primary_active_width> <s_primary_active_height>
  sticky: no

A matcher, then what the window's placement should be. Placeholders still work in any value.

Every tracked layout was converted mechanically, then checked: all nine resolve to the same relayout commands as before. The one exception is the top-term rules' Sticky {..} and Iconhidden {..} lines. Those aren't Fluxbox commands and never did anything, so they were dropped rather than turned into a real stick or unstick.

The old form is now rejected with an error that points at the new one, so a stale layout fails loudly instead of placing nothing.

  • Command order is fixed: SetHead, SendToWorkspace, ResizeTo, MoveTo, stick, then relayout_command. Resizing before an anchored move (Center and friends) used to be a hand-maintained comment; now it is guaranteed.
  • Coordinates carry over unchanged. In Fluxbox's source, MoveTo and [Position] both measure from the window's head and accept the same corner names.
  • Screens by name are new. screen: celtic finds the laptop whether it is primary or secondary, which is how the agent-browser rule works.
  • Removed placeholders: <stick>, <unstick> and <place_RHS> are gone from the parser; celtic+ultrawide spells out its column-3 placement instead.

First match vs last match

This is the one real semantic gap between the two mechanisms:

Relayout

Applies every matching rule in order, so the latest rule wins. A specific rule (mutt's kitty) placed after a generic one (all terminals) overrides it.

Apps file

Uses only the first matching [app] block and ignores the rest.

The generator bridges this:

  1. Placement blocks are written latest rule first, so the rule that wins on relayout also wins on open.
  2. Rules with identical match text merge into one block, later fields winning. For example, the two browser rules for (Head=2), one for geometry and one for sticky, become one block.
  3. An apps.in block with exactly the same pattern joins that block, so agent-browser keeps FocusProtection and gains its head.
  4. The rest of apps.in follows, in its own order.
Known limit. If two rules have different patterns that both match a window, the window gets only the later rule's fields when it opens, not a merge of both. For example, mutt's kitty window opens centred but not resized. That is what the old apps file did too.

apps.in: the hand-written part

  • .fluxbox/apps moved to .fluxbox/apps.in, and .fluxbox/apps is now gitignored like keys.
  • It keeps only non-placement settings: Layer, Hidden, Sticky, Deco, IconHidden, FocusNewWindow, FocusProtection and transient rules.
  • Placement keys are refused. [Head], [Position], [Dimensions] or [Workspace] in apps.in makes planning fail with "window placement belongs in .fluxbox/layouts".
  • Pattern text must match exactly for a block to join a layout rule. That's why the Code/Cursor block now reads (class=Cursor|Code), the layout's spelling.
  • Blocks with no layout rule (Workrave, eog, ksnip, the (head=2) catch-all) come after all placement blocks. So they only reach windows no layout rule matches.

Workspaces and map: no

A literal translation would have sent every new Firefox and gitk window to workspace 3, and every new btop to workspace 6. Workspace 6 is where fluxbox-focus-or-launch hides windows, so btop would have opened hidden. You chose to keep today's behaviour:

  • Moved on open, as before: chat apps (workspace 4), Notion and LM Studio (workspace 3).
  • Moved on relayout only: Firefox, gitk, Kraken, Chrysalis, the single-screen pavucontrol and Blueman, the Chrome title rules, and btop.

Each relayout-only workspace move is split into its own rule:

- match: (Class=firefox)
  screen: primary
  position: <s_primary_col1_left> <s_primary_row1_top>
  size: <s_primary_active_width> <s_primary_active_height>

# Relayout only: a new window opens on the current workspace.
- match: (Class=firefox)
  workspace: 3
  map: no

When the apps file is written and loaded

  1. Plan: on each monitor change the controller's planner reads apps.in (now a hashed planning input like keys.erb) and renders the apps file as a plan artifact. The plan schema went from version 5 to 6.
  2. Prepare and finalize: both workers write ~/.fluxbox/apps right after ~/.fluxbox/keys, by atomic rename.
  3. Restart: the in-place Fluxbox restart that already follows loads it fresh. No Reconfigure is sent.
  4. Bootstrap: if no apps file exists, the post-stow hook (.cfg-post.d/desktop-config) copies apps.in into place. That gives you every setting except placement until the first relayout.
Why not rely on Fluxbox's own reload? Fluxbox rereads the apps file when its ctime changes, but checks only whole seconds, and closing a window also triggers the check. In testing on 2026-10-14, only 20 of 34 edits took effect, and a miss left the window with no rule at all. Likely cause (unconfirmed): a reload read a half-written file. The restart sidesteps that.

How to edit

Place a new kind of window

- match: (Class=Signal)
  screen: primary
  workspace: 4
  position: <s_primary_col1_left> <s_primary_row1_top>
  size: <s_primary_active_width> <s_primary_active_height>

Put it in a common/ include if every layout wants it, or inline in one layout. Put it after any broader rule it should override.

Move it on relayout but not on open

Add map: no to the rule, or split out just the fields that should be relayout-only, as the Firefox workspace rule does.

Add a non-placement setting

Add a block to .fluxbox/apps.in. If the window also has a layout rule, copy that rule's match: text exactly into the block's pattern so the two merge. Otherwise Fluxbox will see the placement block first and never reach yours.

Check it

cd .local/lib/monitor-controller && uv run pytest -q

tests/monitor_controller/test_layout_rules.py covers the fields, and test_fluxbox_apps.py covers the generator. That includes agent-browser in both external layouts and btop never opening on workspace 6.

Limits and open ends

  • Overlapping patterns don't merge on open. See the note under first match vs last match.
  • Title rules rarely fire on open. Chrome sets its real title after mapping. Because the browser (Head=N) blocks come first, title rules mostly apply on relayout only, as before.
  • Fluxbox's Remember menu writes into the generated file, so the next relayout overwrites anything saved from it.
  • Gap after merging. The merge deletes the tracked .fluxbox/apps in the main checkout. Fluxbox has no apps file until mr stow or the next relayout.
  • Follow-up dc-gqkz ("(head=2) sticky rule in .fluxbox/apps.in makes the wrong screen sticky in some layouts"). It has the same head-number problem: under celtic+external-secondary, new windows on the external screen probably become sticky.
