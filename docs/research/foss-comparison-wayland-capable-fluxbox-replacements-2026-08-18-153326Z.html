Wayland-capable Fluxbox replacement comparison

A corrected, repository-specific comparison which treats a credible Wayland future as mandatory. It ranks dual-backend projects for a staged X11→Wayland transition separately from Wayland-native compositors, while preserving the hard requirement for the YAML-driven floating autolayout engine.

Revised conclusion

X11-only projects are no longer recommendations. pekwm and FVWM3 remain useful evidence that Fluxbox parity is possible, but they are technological dead ends under the new requirement. AwesomeWM and XMonad are excluded for the same reason.

Track A — staged migration while still on X11

  1. KWin first for desktop-semantic parity. Test kwin_x11 --replace now, preserve six global desktops and sticky secondary-output windows, then move the same rules/script concepts to KWin Wayland. It best preserves traditional floating interaction, titlebars, strict focus and multi-output semantics.
  2. Qtile first if the layout engine dominates the decision. Its Python command graph is cleaner than KWin scripting and most configuration is backend-neutral. The costs are per-screen group semantics, weaker decorations and no native floating tab groups.
  3. Enlightenment only as a short discovery spike. It is genuinely dual-backend and unusually close to Fluxbox’s floating/grouped UX, but the trial must prove supported enumeration and mutation of existing windows before any port begins.

Track B — switch WM and display protocol together

  1. Wayfire is the best match to the repository’s defining architecture: external Python can enumerate windows and apply geometry, output, workspace, sticky, alpha and state through IPC.
  2. Sway has the most mature, stable and inspectable IPC. An all-floating profile is practical, but its workspace/container model is a deliberate UX compromise.
  3. Hyprland provides the closest Wayland equivalent to Fluxbox grouping/tabs and pinning. Its faster-changing 0.x interface should be hidden behind a backend adapter.
  4. Pinnacle is architecturally attractive because configuration itself is a gRPC client, but it is not mature enough to make the primary migration target.
  5. labwc is the manual-UX winner but cannot satisfy imperative relayout of arbitrary existing native Wayland windows without a fork.

Overall recommendation: run two bounded prototypes, not eight: KWin on X11 for the staged track and Wayfire in a nested/direct Wayland session for the native track. The outcome will reveal whether preserving global desktops/titlebar UX or preserving the external layout engine is harder in practice.

Repository requirements retained from the Fluxbox audit

  • Imperative existing-window relayout is mandatory: bin/desktop-layout applies ordered actions to every current match, not only mapping-time rules.
  • The YAML geometry model survives: includes, topology placeholders, margins, named regions and sublayouts.yaml remain more flexible than adopting a compositor’s default tiler.
  • Multi-head is semantic: stable primary/secondary identities, hotplug, reserved panel/log regions, exact logical geometry, proportional moves and laptop/ultrawide/three-monitor profiles.
  • Workspace behaviour matters: six global Fluxbox workspaces plus sticky secondary-head clients are not equivalent to independent workspace sets on every output.
  • Window identity changes: native Wayland exposes app_id/title, while XWayland retains class/instance/role. Every current match must be audited.
  • Floating UX matters: strict mouse focus without raise, conventional titlebars, shade, modifier drag, layers/above/below, opacity, key modes and focus-or-launch.
  • Grouping is real but narrow: browser attachment is scripted in one layout, while tab controls are globally bound. Losing it must be explicit.
  • Wayland coordinates are logical: mixed fractional scale invalidates assumptions that XRandR pixel dimensions equal compositor geometry.
  • The panel/session stack changes: X11 tray selections, wmctrl, xdotool, xprop, X IDs and autorandr cannot manage native Wayland clients/outputs.

KWin

Verdict and best fit: Best staged migration when traditional floating interaction, global desktops, sticky secondary windows and mature multi-head behaviour are weighted above a simple shell IPC.

GitHub starsN/A: canonical forge is KDE GitLab; GitHub mirror had 680 on 18 August 2026
MaintenancePlasma 6.7.4 on 4 August 2026; canonical development is continuous; GitHub mirror recorded 2,097 commits in the common window
LicenceGPL-2.0-or-later overall

Domain fit

KWin supplies native floating placement, server decorations, shading, snapping/quick tiling, strict focus-under-mouse independent of raising, per-window rules, all-desktops state, above/below, opacity, no-border and rich JavaScript/QML scripting. Current KWin no longer has the historic grouped titlebar tabs.

Backend and multi-head behaviour

kwin_x11 can replace Fluxbox in the current X session. kwin_wayland is a native compositor with XWayland, but its supported deployment expects a desktop shell—normally Plasma. Outputs expose connector, make/model/serial, logical geometry, scale and hotplug signals. Global virtual desktops remain the default; secondary-output windows can be onAllDesktops. KWin 6.7 even bundles a “Virtual Desktops Only on Primary” script implementing almost exactly the current sticky-secondary convention. KScreen should replace, not compete with, autorandr.

Autolayout backend

A persistent KWin script can call workspace.windowList(), match class/resource/role/title, and mutate frame geometry, desktops, output, all-desktops, opacity, above/below and border state. The weakness is packaging an external request channel: D-Bus can load/control scripts but is not a Qtile-like direct mutation API. The clean design is a small long-lived KWin script receiving structured layout requests.

Popularity

GitHub stars are not representative because the canonical project is on KDE Invent and ships as a core Plasma component. The non-canonical mirror had 680 stars; the installed/deployed Plasma user base is the meaningful adoption signal.

Maintenance

KWin follows KDE Plasma’s regular feature and bug-fix cadence. Plasma 6.7.4 shipped 4 August 2026 and the mirror had over two thousand commits in the common window.

Licence

KWin is GPL-2.0-or-later overall, with per-file SPDX declarations for components.

Strengths and trade-offs

Strongest global-desktop and floating-UX match; mature fractional scaling and hotplug. Costs: likely transition from XFCE panel to Plasma shell on Wayland, JavaScript bridge engineering, and no Fluxbox-style tabs.

Qtile

Verdict and best fit: Best staged option when preserving Python programmability and one shared policy across X11 and Wayland is the overriding goal.

GitHub stars5,287 as of 18 August 2026 UTC
Maintenance577 commits in the common window; v0.37.0 on 8 August 2026; latest commit 11 August
LicenceMIT

Domain fit

Qtile exposes matching, floating geometry, groups, screens, hooks, focus and window state directly to Python and through its command graph. This maps cleanly to liblayout.py. It lacks conventional compositor titlebars, native arbitrary floating tabs, Fluxbox’s layer hierarchy and a normal sticky-window primitive.

Backend and multi-head behaviour

Qtile runs as an X11 WM or wlroots-based Wayland compositor with optional XWayland. Most layouts, groups, keybindings and hooks are shared. X11 observes RandR; Wayland implements wlr-output-management. generate_screens(outputs) can create topology policy by count, port, model or serial—an excellent fit for the repository’s dock profiles. Each screen displays one group and a group is attached to at most one screen, unlike Fluxbox’s one global current desktop.

Autolayout backend

The command client can enumerate and mutate windows, while custom Python functions can expose exactly the layout operations required. The same neutral adapter can work on both backends; only identity and output discovery differ. Native Wayland uses app-id/title, while X11/XWayland preserve richer properties. Official documentation still warns about incomplete Wayland functionality and an XWayland pointer-routing bug.

Popularity

The canonical repository had exactly 5,287 stars.

Maintenance

Qtile had the strongest conventional release cadence among programmable dual-backend WMs: 577 commits in the common window and v0.37.0 ten days before this report.

Licence

MIT, an OSI-approved permissive licence.

Strengths and trade-offs

Strongest shared-source migration and easiest layout adapter. Trade-offs are tiling-first ergonomics, screen/group semantics, sparse decorations, no native tabs, and more policy code to emulate sticky secondary windows.

Wayfire

Verdict and best fit: Best Wayland-native prototype for retaining the external, imperative YAML layout architecture.

GitHub stars3,032 as of 18 August 2026 UTC
Maintenance206 commits in common window; v0.11.0 on 27 July 2026; latest commit 11 August
LicenceMIT

Domain fit

Wayfire is a plugin-based Wayland stacking compositor with SSD titlebars, modifier/titlebar move-resize, snapping/grid, alpha, sticky and above/below actions. It has no supported Fluxbox-like tab/group container and no shade-equivalent was found.

Backend and multi-head behaviour

Wayland-native with optional XWayland. Outputs support exact position, mode, transform, fractional scale, mirroring, HDR and colour profiles. wlr-output-management allows Kanshi profiles; IPC emits output-layout changes. Workspaces are normally independent 2-D grids per output, so global six-workspace switching needs a small script that changes every output together.

Autolayout backend

ipc-rules can list views with ID, PID, app-id, title, geometry, output, workspace/layer/state and configure exact geometry/output/sticky/tiled/fullscreen state. Additional plugins expose workspace movement, top/bottom, alpha and pre-map policy. Official pywayfire already includes layout, move, opacity and session-restore examples. This is the closest native equivalent to fluxbox-remote Map.

Popularity

3,032 stars—smaller than Sway/Hyprland, but a meaningful floating-compositor community.

Maintenance

Active 0.11 development, 206 commits in the common window and a release three weeks before observation.

Licence

MIT.

Strengths and trade-offs

Best direct control and good XFCE 4.20 panel test history. Gaps: per-output workspace model, no tabs/shade, plugin composition/versioning, and conversion to logical coordinates/app-id matching.

Sway

Verdict and best fit: Best long-lived, queryable command substrate if an all-floating profile on an i3-style compositor is acceptable.

GitHub stars17,250 as of 18 August 2026 UTC
Maintenance105 commits in common window; 1.12 on 25 May 2026; latest commit 31 July
LicenceMIT

Domain fit

Sway can force every normal window floating, supplies compositor titlebars, criteria, modifier drag, focus-follows-mouse, sticky floating windows and tabbed/stacked tree containers. Floating tabs are not Fluxbox arbitrary-frame attachment, and shade/layers are absent.

Backend and multi-head behaviour

Wayland-native with XWayland. GET_OUTPUTS returns connector, make/model/serial, modes, logical rectangle, scale, transform and current workspace. Output rules can match stable identifiers and hotplug reapplies configuration. Workspaces are globally named but each is visible on one output; sticky is output-scoped.

Autolayout backend

swaymsg -t get_tree -r gives a complete JSON tree. Criteria include native app-id and XWayland class/instance/title/role, PID, container ID, marks, workspace and state. Exact commands set floating, pixel geometry, output, workspace, sticky and opacity. This is stable and easy to test, making it an excellent backend despite the UX mismatch.

Popularity

17,250 stars and broad distribution adoption.

Maintenance

105 commits and release 1.12 in the common window. Maintainers deliberately prioritize stability, reliability and performance over feature growth.

Licence

MIT.

Strengths and trade-offs

Most durable IPC and excellent inspection/matching. Costs: opinionated container/workspace model, no native Fluxbox-style floating groups, output-scoped sticky and likely replacement of XFCE panel with Waybar/swaybar.

Hyprland

Verdict and best fit: Best Wayland option when grouped floating tabs and pinning are more important than conventional titlebars and API stability.

GitHub stars37,938 as of 18 August 2026 UTC
Maintenance1,367 commits in common window; v0.56.2 on 5 August 2026; latest commit 17 August
LicenceBSD-3-Clause

Domain fit

Hyprland supports a practical all-floating profile, exact pixel dispatchers, rich regex selectors, modifier movement, pinning, z-order changes and native window groups with groupbar tabs. It lacks conventional built-in titlebars; hyprbars is a version-coupled plugin.

Backend and multi-head behaviour

Wayland-native with XWayland. Monitor JSON includes connector, description/make/model/serial, mode, logical position, scale, transform, active workspace and reserved margins. Rules can match stable descriptions; hotplug events are available. Workspaces bind to monitors and pinning is monitor-scoped, unlike global Fluxbox desktops.

Autolayout backend

hyprctl clients -j plus monitor/workspace/event sockets provide discovery. Address-targeted dispatchers set exact move/resize, workspace, floating and grouping. Dynamic rules set opacity and decorations. The interface is capable, but rapid 0.x change makes a narrow adapter and compatibility tests mandatory.

Popularity

37,938 stars—the largest current community signal in this shortlist.

Maintenance

Extremely active: 1,367 commits, current release v0.56.2 and code activity the day before this report.

Licence

BSD-3-Clause.

Strengths and trade-offs

Only mature candidate with a strong native grouped-window story close to Fluxbox tabs. Trade-offs: no standard titlebar, per-monitor workspace model, plugin/version churn and a more animated/opinionated default which must be pared back.

Enlightenment

Verdict and best fit: Genuine dual-backend floating desktop with promising grouping UX, but only a bounded trial should determine whether supported external control is sufficient.

GitHub starsN/A: canonical self-hosted forge; current GitHub mirror had 3
Maintenance173 mirror commits in common window; 0.27.1 released 14 March 2025; latest mirror commit 8 July 2026
LicenceBSD-2-Clause

Domain fit

Enlightenment is a full floating desktop with server decorations, remember rules, sticky, shade, layer/opacity concepts and interactive stacking/grouping close to Fluxbox. Much configuration is GUI-managed opaque Eet state rather than a reviewable text program.

Backend and multi-head behaviour

E genuinely operates as an X11 WM and native Wayland compositor with XWayland. Profiles share much configuration, though identifiers and output state differ. Outputs are zones; every zone has its own desk grid and current desk, with sticky windows visible across desks on their zone—not Fluxbox global workspaces.

Autolayout backend

enlightenment_remote and the message-bus module control desktop/session concerns, but no documented stable API was found that combines arbitrary-client enumeration, exact geometry/output/desk and state/group mutation. An in-process C module could, but that couples the repository to E internals. This is the trial’s go/no-go gate.

Maintenance

E27 remains maintained, with 173 mirrored commits in the common window and changes through July 2026, though releases are less frequent than KDE/Qtile.

Licence

Enlightenment uses BSD-2-Clause; EFL dependencies have their own licences.

Strengths and trade-offs

Potentially the closest dual-backend manual UX, including grouping. The decisive weaknesses are opaque configuration, per-zone desks and unproven external automation.

Pinnacle

Verdict and best fit: Most interesting young programmable Wayland architecture; watch and prototype narrowly, but do not anchor the migration to its pre-1.0 API yet.

GitHub stars617 as observed 18 August 2026 UTC
Maintenancev0.2.3 on 3 February 2026; meaningful commits through 27 June 2026
LicenceGPL-3.0-only

Domain fit

Pinnacle is an Awesome-inspired Smithay compositor whose configuration is deliberately a separate gRPC client. Official Lua/Rust APIs expose windows, tags, outputs, signals and layouts; Python bindings could be generated. Floating geometry is controllable, but conventional Fluxbox decorations/group tabs are absent.

Backend and multi-head behaviour

Wayland-native with XWayland. Output callbacks run for current and newly connected displays; APIs set global location and adjacency. Tags belong to outputs; a window can have multiple tags, but cross-output tag association is explicitly undefined. This is flexible but not the global Fluxbox workspace model.

Autolayout backend

The gRPC Unix socket is conceptually ideal: get all window handles, subscribe to signals and issue geometry/tag/output/state operations from a config client. A Python client or small Lua/Rust bridge can host the existing YAML. The risk is API maturity, incomplete polish and a smaller tester base.

Popularity

617 stars: healthy interest for a young niche compositor, far below mature alternatives.

Maintenance

Active pre-1.0 development with v0.2.3 in February and fixes through June 2026.

Licence

GPL-3.0-only based on the distributed GPLv3 text and repository metadata.

Strengths and trade-offs

Cleanest future-facing client/server configuration architecture. Trade-offs are youth, tag/output semantics, missing traditional floating chrome/tabs and maintaining a client bridge.

Domain fit

Backend and multi-head behaviour

Wayland-native with optional XWayland. Kanshi/wlr-randr configure output position, mode, transform and scale; hotplugged DRM outputs auto-enable. Methodology and shortlist

The requirement was changed after the first report: a candidate must have a maintained native Wayland path. X11-only projects were therefore removed regardless of Fluxbox similarity. Candidates were split into genuine dual-session projects and Wayland-native compositors; a nested Wayland compositor running on an X11 backend does not count as an X11 WM migration stage.

The shortlist includes the serious programmable/floating options found: KWin, Qtile and exploratory Enlightenment for dual-backend migration; Wayfire, Sway, Hyprland, Pinnacle and labwc for Wayland-native migration. Mutter/GNOME Shell and Muffin were excluded because their supported external arbitrary-window policy surfaces are weaker and desktop-shell coupling is stronger. River and niri remain watchlist projects: both are active, but their tag/scrolling models and control surfaces are worse matches. Xfwm4 is not itself a Wayland compositor.

Maintenance uses a common 12-month window. GitHub counts were observed through API/search where the canonical project uses GitHub. KWin and Enlightenment correctly show N/A because their canonical forges are elsewhere; mirror counts are labelled. Popularity is contextual, not a quality score. No compositor was installed or run during this research, so real browser app-ids, pointer-focus races, mixed-scale geometry, panel/tray behaviour and hotplug convergence remain prototype questions.

Prototype plan and acceptance gates

  1. Normalize the layout engine first: compile YAML into structured operations—match, output, workspace/tag, logical geometry, sticky/pin, opacity, stacking, decoration and group—without Fluxbox command strings.
  2. KWin staged spike: run kwin_x11 --replace, build a tiny script request bridge, apply one full topology and all ly sublayouts, then verify global desktops and sticky secondary outputs. Stop if external requests cannot be made reliable.
  3. Wayfire native spike: run nested for safety, enumerate views through pywayfire, apply the same operation fixture in logical coordinates, then test direct output hotplug/Kanshi.
  4. Compare hard failures: KWin’s script bridge/Plasma-shell coupling versus Wayfire’s per-output workspaces/no-tabs. Pick the smaller long-term compromise.
  5. Only then evaluate alternatives: Qtile if shared Python backends are decisive, Sway if API stability is decisive, Hyprland if grouping is decisive.
  6. Wayland acceptance suite: native and XWayland identity matching; three monitor topologies and fractional scaling; repeated dock/DPMS; focus without raise; active-window sublayouts; full autolayout; focus-or-launch; panel/tasklist/tray; client survival across compositor config reload; browser grouping decision.

Do not port the 229 bindings first. A candidate fails early if it cannot deterministically relayout existing native windows after output changes. Prove that vertical slice before investing in menus, themes or shortcut parity.
